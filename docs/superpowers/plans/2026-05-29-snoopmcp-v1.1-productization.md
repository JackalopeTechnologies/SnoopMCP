> **For agentic workers:** v1 (read-only, 19 tools, HTTP MCP, real injection) is **complete and proven** — see `docs/superpowers/plans/2026-05-27-snoopmcp-v1-readonly.md`. This plan covers the productization arc on top of it. **Goal:** Make SnoopMCP self-service end-to-end: the LLM can discover targets, a guided walkthrough shows it all working on the sample app, and a WiX installer deploys the host (per-user autostart), packages the sample, and registers SnoopMCP into VS Code Copilot + Claude Code.

## Locked decisions (do not relitigate)

- **Run model: per-user logon autostart**, NOT a session-0 Windows service. SnoopMCP injects into the user's *interactive-session* WPF apps; the proven path (smoke + integration tests) is host + target as the same user in the same session. SaddleRAG runs LocalSystem session-0 fine only because it never leaves its own process — that precedent does **not** transfer. (A session-0 service *might* work via machine-global pipes/localhost + SeDebugPrivilege, but it's unproven and risky; rejected for v1.1.)
- **Transport:** HTTP (Streamable HTTP) on `http://127.0.0.1:6300/mcp`. Unchanged.
- **Injection:** subprocess `injector/Snoop.InjectorLauncher.x64.exe` with `--settingsFile <pipeName>`; payload `AssemblyResolve` bootstrap; `injector/` + `payload/` staged next to the host. Unchanged.
- **x64 only.** Build needs VS + the C++ x64 workload (the native `Snoop.GenericInjector.vcxproj`).

## Workstream A1 — Finish `listWpfProcesses` (process discovery)

**Why:** `attach(pid)` needs a PID the LLM can't get on its own over MCP. `listWpfProcesses()` is host-side, pre-attach discovery so the LLM can pick a target by name/title. Spec §9 deferred it; we're pulling it forward (cheap, high-leverage).

**State:** WIP on branch `task-34-list-processes` (commit `d6fa02e`). DONE: `WpfProcessDto`, `ListWpfProcessesResponse` (`src/SnoopMCP.Protocol/Tools/`), `ProcessEnumerator` (`src/SnoopMCP.Host/Injection/`). The enumerator filters to processes with a main window, scans modules for `PresentationFramework.dll`, reads bitness (`IsWow64Process`) + runtime (`hostfxr.dll`), skips inaccessible processes (`Win32Exception`/`InvalidOperationException`/`NotSupportedException`).

**Remaining steps:**
1. Resume the branch: `git checkout task-34-list-processes` (do NOT branch fresh off master — the WIP is here).
2. Add `McpTools.ListWpfProcesses` (host-side; does NOT go through the pipe):
   ```csharp
   [McpServerTool, Description("List running WPF processes that can be attached to (pid, name, window title, bitness).")]
   public Task<JsonElement> ListWpfProcesses(CancellationToken cancellationToken)
   {
       cancellationToken.ThrowIfCancellationRequested();
       var enumerator = new SnoopMCP.Host.Injection.ProcessEnumerator();
       var response = new ListWpfProcessesResponse(enumerator.ListWpfProcesses());
       return Task.FromResult(SerializeResult(response));
   }
   ```
   (No `McpTools` ctor change → no integration-test ctor change. `ProcessEnumerator` is stateless; inline `new` is fine.)
3. Host.Tests: a robustness unit test — `ProcessEnumerator().ListWpfProcesses()` returns non-null and does not throw (don't assert specific contents; the test host isn't WPF, so contents are machine-dependent/flaky).
4. IntegrationTests: a new `[Fact]` — call `mTools.ListWpfProcesses`, assert the launched `SampleWpfApp` appears (match on `processName == "SampleWpfApp"`) with `attachable == true`. (Shares the `IAsyncLifetime` sample process.)
5. README: add a `listWpfProcesses()` row to the tool table; bump "Nineteen read-only tools" → "Twenty". Note it's host-side discovery (works before attach).
6. Build (`dotnet build SnoopMCP.sln -c Debug` — zero warnings), run tests, commit, PR, merge.

**Analyzer notes:** `ProcessEnumerator` already uses the established patterns (const strings for module names, no `out` except the grandfathered P/Invoke pattern, specific catch filter). Verify STY0008 on any new literals in the McpTools description.

## Workstream A3 — WiX installer (STRUCTURAL — give this its own writing-plans pass)

**Mirror SaddleRAG, with the run-model swap.** SaddleRAG already provides the patterns; read its live files before writing:
- `E:/GitHub/SaddleRAG/SaddleRAG.Installer/Package.wxs` — WiX (modern v4/v5) package structure, `ServiceInstall`/`ServiceControl` (we replace these with a scheduled task), custom-action start + `/health` gate.
- `E:/GitHub/SaddleRAG/SaddleRAG.ClientIntegration/Writers/{VsCodeMcpWriter,ClaudeCodeWriter,ClaudeDesktopWriter}.cs` + their tests in `SaddleRAG.Tests/ClientIntegration/` — the exact MCP-client registration logic. We need VS Code (Copilot) + Claude Code.
- `E:/GitHub/SaddleRAG/SaddleRAG.Mcp/Program.cs` ~line 122 — `UseWindowsService` (we will NOT use this; we run in-session).

**Proposed task breakdown (to be detailed in a dedicated plan):**
1. **`SnoopMCP.ClientIntegration`** library — `VsCodeMcpWriter` + `ClaudeCodeWriter` that register an **HTTP** MCP server entry pointing at `http://127.0.0.1:6300/mcp` (idempotent add/remove). Port both from SaddleRAG, adapting stdio→HTTP entry shape. Unit-test each writer against temp config files (SaddleRAG's tests are the template).
2. **`SnoopMCP.Cli`** (the "management exe") — `register` / `unregister` (invokes the writers), `status` (probe `:6300/mcp` reachability + whether the autostart task exists), `start`/`stop`. The installer calls `register`; the user can re-run it.
3. **Per-user autostart** — register a logon **scheduled task** (`schtasks` / Task Scheduler COM) that launches the SnoopMCP **tray app** (Workstream B) in the interactive session at sign-in, non-elevated. The tray app supervises/launches `SnoopMCP.Host.exe` and is the user-facing status surface. (NOT a service.) Provide an elevated path for debugging elevated targets (the tray app offers "restart elevated", or a separate elevated task variant). If the tray app isn't built yet, the task can launch the host directly as an interim step.
4. **`SnoopMCP.Installer`** (WiX `Package.wxs`) — install host + `injector/` + `payload/` + the CLI to Program Files; run `SnoopMCP.Cli register` + create the logon task as custom actions on install, and reverse on uninstall. Package **SampleWpfApp** under a `samples/` install dir + a Start-menu shortcut so users have a target to try. Version from the build (mirror SaddleRAG's `Version` wiring).
5. **CI consideration** — the native injector build needs the C++ workload on the build agent; the installer build needs the WiX toolset. Document agent requirements.

**Open questions for the installer plan:**
- Per-user install (no elevation, `%LocalAppData%`) vs per-machine (Program Files, needs elevation)? Per-machine + per-user logon task is typical; decide in the dedicated plan.
- Elevated-target debugging: ship a second elevated autostart, or a tray/menu "restart elevated"? (Ties into Workstream B.)
- Port 6300 collision if multiple users log in concurrently — acceptable for v1.1; note it.

## Workstream B — Per-product tray apps (one per repo)

**Idea (from the user):** **three separate** system-tray apps — one each for **SnoopMCP, SaddleRAG, AeroCoder** — each living in **its own product repo**, each **autostarted at logon**, showing that product's running state and a quick link to its UI. Not one cross-product dashboard; three independent, consistent apps.

**Per-app behaviour:**
- Tray icon reflects state: running / stopped / unreachable / error.
- Menu: Open UI (launch browser to the product's UI), Start / Stop, Status, Exit.
- Polls its own product's localhost health endpoint on an interval.
- Autostarts at logon (same per-user logon-task pattern as A3 — in the interactive session).

**Icons — solved without hand-drawn art:** the tray icon is **rendered at runtime** with `System.Drawing` — draw a letter badge (e.g. "S"/"R"/"A") tinted by state (green=running, gray=stopped, red=error) onto a 32×32 bitmap and set `NotifyIcon.Icon` via `Icon.FromHandle(bitmap.GetHicon())` (remember `DestroyIcon` to avoid a handle leak). No `.ico` asset required; a designer can replace with polished art later. The exe's taskbar/Explorer icon can use a simple generated placeholder `.ico` for now.

**SnoopMCP's tray app is part of SnoopMCP's scope** (this repo) and should double as SnoopMCP's **in-session presence**: the logon autostart (A3) launches `SnoopMCP.Tray`, which supervises/launches `SnoopMCP.Host.exe`, shows status (probe `:6300/mcp`), and links to the future monitor UI. This unifies A3's "autostart" with the tray idea — the tray app *is* the autostart vehicle.

**SaddleRAG + AeroCoder tray apps** are parallel work in their own repos (not this plan's concern), but a **shared skeleton** keeps the three consistent: a tiny reusable tray-app template (NotifyIcon host + runtime icon renderer + health-poll loop + descriptor of {name, health URL, UI URL, start command}). Consider extracting the skeleton once SnoopMCP's is proven, so SaddleRAG/AeroCoder copy a known-good pattern.

- **SnoopMCP**: health = `http://127.0.0.1:6300/mcp` reachable; UI = future monitor (deferred).
- **SaddleRAG**: its MCP port + `/monitor` Blazor UI (root `/` redirects there).
- **AeroCoder**: confirm its port + UI endpoint.

**Tech:** WinForms `NotifyIcon` (simplest tray story) or WPF, .NET 10, single-instance, per-user logon autostart.

**Status for this plan:** the **SnoopMCP tray app** folds into SnoopMCP v1.1 as the A3 autostart presence (do it as part of / right after the installer). The SaddleRAG and AeroCoder tray apps are noted for their own repos.
